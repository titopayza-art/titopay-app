Build: admin-console-v74
Date: 2026-08-08

v74 - Analytics and Service Builder are readable, and their cache stamp is
correct for the first time since v63.

  - assets/admin-analytics.js and assets/admin-service-builder.js are grouped
    into ten and eleven named sections with a contents list at the top of each,
    the same convention admin.js already follows. Only function declarations
    moved, and a function declaration is hoisted before any statement in the
    module runs, so no behaviour changed. Module state, the lookup tables and
    the exported entry point kept their exact original order.
  - admin.js requested both modules at a version it wrote down separately from
    the one in the page markup, and the two had drifted: pages were served at
    v73 while the modules were still fetched at ?v=admin-console-v63. Ten
    console builds therefore shipped against cached modules. admin.js now reads
    its build stamp off its own script tag, so the two can never disagree again.
  - assets/titopay-logo.jpg is gone. The sign-in panel has used the wordmark
    since v73 and nothing referenced the JPEG. Delete it from the server if an
    earlier upload left it there.

v66 - The Dashboard provider tile counts connected providers again.

  - Platform health read a top-level `status` field on each provider record.
    That field does not exist - the state lives in `health.status` - so the tile
    reported "0 of N active" no matter how many providers were connected. It now
    counts with the same rule the Integration Centre uses, so the two pages can
    never disagree.

v65 - The Payout capability is configurable and testable from the provider
cards too, not only the Peach Payments page.

  - API Provider Settings and the Integration Centre render one Configure panel
    per capability on the Peach card, each with its own fields, Save
    Configuration and Test Connection. Previously the payout status appeared on
    the card but there was no way to configure or test it from that page.
  - The parent Peach chip reads Partially configured while one capability is
    connected and the other is not.

v64 - Peach Payments splits into two independent capabilities.

  - The Peach Payments provider page now shows Collection / Top-up and
    Payout / Withdrawal as separate sections, each with its own environment,
    base URL, credentials, status, last successful test, response time,
    Save Configuration and Test Connection. The two never share a status:
    Collection can read Connected while Payout reads Not Configured, and the
    parent card reads Partially configured rather than Connected.
  - Each section posts to its own provider key, so saving one capability
    cannot overwrite the other's stored credentials. Secrets stay encrypted
    server-side and continue to appear only as masked values.
  - A capability that has never been tested and has nothing configured now
    reads Not Configured rather than Not Tested.
  - Requires the API package of the same date, which registers the payout
    capability. Without it the page renders Collection exactly as before.

v63 - Reject, with a written reason, on every marketing approval queue.

  - The PWA Announcement, SMS and Email Production approval queues now show
    Reject beside the approve action on every pending item - approving is no
    longer the only way to clear the queue. Rejecting always asks for a
    reason (required, up to 500 characters); the queue then shows
    "Rejected by <role>: <reason>" on the row and the status chip reads
    rejected. An approver who already recorded their approval on a pending
    announcement can still reject it while it waits for the second role.
  - The reject calls POST the reason to
    /admin/marketing/{sms-campaigns|email-campaigns|announcements}/:id/reject.
    The contract - pending-only, same CEO/COO/owner roles as approving,
    reason stored on the row, audit entry - is specified as A-P1-8 in
    ADMIN-API-REQUIREMENTS.md. If the API does not implement an endpoint yet
    the console says so and confirms the item is unchanged.
  - The CI gate grew to 43 checks: every queue offers reject, and a
    rejection's reason is shown on the queue after the action.

v62 - Personal and business accounts can be delinked from the portal when a
customer asks for it.

  - The Users page shows "Linked: <business>" under the account type for any
    user record that carries a linked business, and a Delink business action
    beside Suspend and Lock. The action states plainly what happens - both
    profiles stay active and keep their own wallets and balances, only the
    connection is removed - and asks for confirmation before calling the API.
  - The Global Search profile card gains a Linked Business fact. It reads
    "None reported" rather than "Not linked" when the API sends no linkage
    field, because the console cannot tell the difference.
  - The console reads every linkage field name the API might use
    (linked_business object, linked_business_id/_name/_wallet,
    business_link_id, business_linked) and calls
    POST /admin/users/:id/delink-business with the linked business id. The
    full contract, including the rules the API must enforce (no profile
    closed, no balances moved, stale-id rejection, audit entry), is
    specified as A-P1-7 in ADMIN-API-REQUIREMENTS.md. If the endpoint is not
    implemented yet the console says so and confirms nothing was changed.
  - The CI gate grew to 41 checks: linked users offer the action, and
    delinking separates the accounts and refreshes the list.

  - Informational field hints no longer render in the Caps Lock warning

v56 - Low-Code Service Builder. A new Platform module for creating and
managing TitoPay service definitions entirely through configuration - never
code. Nothing an operator types is ever executed: every value is data rendered
through the console's escaping, uploads are validated, and hostile SVGs are
rejected outright.

  - Ten-step wizard: basics, branding (drag-and-drop icon, banner, thumbnail
    and feature image with type, size and content validation), navigation,
    permissions, availability with country and future-ready province lists,
    API configuration restricted to TitoPay API endpoints with a safe GET-only
    Test Connection, UI configuration with a live tile preview, fees mapped to
    the catalogue's fee and commission fields, notifications, and a review
    step that blocks publishing until every check passes.
  - Draft and publish lifecycle: nothing is offered until published. Publish,
    disable, archive, restore, duplicate and permanent delete, with typed
    confirmation on every destructive or publishing action.
  - Version history snapshots the full configuration on every publish, with
    one-click rollback that republishes the restored version - history is
    never rewritten. An append-only audit trail records operator, role,
    session, device and detail for every action.
  - Per-service analytics derive live from transactions carrying the service
    code: uses, success and failure counts, daily, weekly, monthly usage and
    recorded revenue. Zeros are stated as zeros - nothing is simulated.
  - Storage is honest about where it lives. If the API exposes
    /admin/service-builder/services the builder uses it as the source of
    truth; until then definitions are stored in this console's registry, the
    page says so, and Export JSON produces both the full definition and a
    catalogue entry in the exact schema the platform's service catalogue
    already consumes (service_code, fee, commission, personal_visible,
    business_visible, sort_order, ...), ready for the API team to load.
  - The module is its own lazily-imported file, so every other console page
    loads exactly the payload it loaded in v55. Access requires platform-owner
    rights or a service-builder permission; no other module's access changed.
  - The CI gate grew again: the builder renders among the now 40 routes, the
    wizard opens, a saved draft appears in the list, and the module stays
    gated for a role without the permission.

v55 - Alert Centre. The platform events that were flooding the owner's inbox
as emails - sign-ins recorded, failed attempts, fraud flags, pending KYC,
waiting customers, failed transactions - now live inside the console.

  - A bell in the topbar of every page carries the unread count. Its panel
    shows the most recent alerts and marks all read in one click.
  - The new Alerts module (sidebar, under Dashboard) is the full centre:
    severity tabs with counts, category filter, unread-only view, pagination,
    mark all read, and every alert links to the module that owns the event.
  - Alerts are derived live from the security, audit, compliance, support,
    transaction, system-health and merchant modules - the same events the
    emails describe. Nothing is invented; a source that does not answer
    contributes no alerts. The feed refreshes every two minutes while the
    console is open.
  - Read state is stored per browser. The API has no alert-read endpoint yet,
    and the page says so rather than pretending the state is shared.
  - The alert emails themselves are sent by the TitoPay API, not this console.
    Now that the events are visible here, the API's notification sender can be
    switched off for routine sign-in mail without losing anything.
  - The CI gate grew to cover it: the alerts route renders, the bell carries
    an unread badge, the panel opens, and mark-all-read clears the badge.

v54 - Bank-grade hardening beneath the interface, and the console gains a
permanent regression gate. No console page behaviour changed.

  - Transport and headers. The .htaccess now sends Strict-Transport-Security,
    Cross-Origin-Opener-Policy and Cross-Origin-Resource-Policy alongside the
    existing headers, denies dotfiles and repository documentation, and its
    Content-Security-Policy drops unsafe-inline for styles and gains the
    wss://api.titopay.co.za entry the pages already declared - without it, a
    host with mod_headers active would have blocked the support chat socket.
  - The sign-in page's own CSP also drops unsafe-inline: no page in the
    console now permits inline styles.
  - Failure surface. Branded 403 and 404 pages replace the server defaults,
    wired through ErrorDocument, with routes back to the dashboard and sign-in.
    robots.txt disallows everything, matching the noindex headers.
  - Release integrity is now enforced, not assumed: a committed test gate
    (tests/admin in the repository, run by CI on every push) verifies one
    version string across all pages, the version file and the deployment
    marker, then drives the real console in Chromium - credential sign-in to
    the dashboard, all 38 routes rendering, the table layer, the analytics
    permission gate and a zero-console-error run.

v52 - Enterprise UI/UX pass. Presentation only: no endpoint, permission,
route, payload or business rule was changed, and a control-by-control
comparison of all 38 routes before and after shows zero removals.

  - Design system. A two-stop elevation ramp replaces the single flat shadow,
    radii and spacing move onto one scale, headings and figures tighten, and
    the muted ink was darkened to clear WCAG AA on card surfaces. Buttons gain
    press feedback and a consistent disabled state; a bare submit button in the
    filter rows no longer renders as browser chrome.
  - Navigation. The rail collapses to icons and remembers the choice per
    browser. Nothing is removed when it does: every item keeps its route, icon
    and accessible name, and the label moves to a tooltip. The state is ignored
    below the tablet breakpoint, where the rail is already a drawer. Escape
    closes the drawer.
  - Tables. Every table in the console gains sortable headers with aria-sort
    and a third click that restores the module's own order, a row filter with a
    live count, bulk selection with select-all, per-table export of what is on
    screen, column resizing, and a sticky header that reads as a layer. The
    layer works on the rendered table through a MutationObserver, so no module
    was modified to receive it and modules that re-render keep it.
  - Prioritisation by colour. A row carrying a red or orange status now shows a
    matching accent on its leading edge, so high-risk compliance reviews,
    flagged transactions and queues waiting on an agent are visible without
    reading. The accent is drawn from the status the module already rendered.
  - Dashboard. Keeps the four figures and the endpoint that produced them, and
    adds wallet float, active sessions, pending KYC, open tickets, merchant
    onboarding, flagged security events, a platform health panel covering API,
    database, providers and sessions, and a live activity feed from the audit
    log. The first paint still comes from the overview endpoint alone;
    everything else arrives after it and never blocks it. A source that does
    not answer leaves a dash.
  - States and feedback. Toasts carry a tone and an icon, inferred from the
    message, so a confirmation and a failure no longer look identical. Empty
    tables explain themselves. A progress line runs under the topbar while a
    module loads. Content settles in rather than snapping, and every animation
    is dropped under prefers-reduced-motion.
  - Accessibility. A visible focus ring is guaranteed console-wide, including
    the rail. Required fields are marked on the label. Pointer targets reach
    44px below the tablet breakpoint. Sortable headers are keyboard operable
    and announce their state.
  - Verified: 38 routes render, no console errors, no horizontal overflow at
    1440, 1280, 1024, 820 or 768, both themes, and page-load timings unchanged
    within run-to-run noise apart from the dashboard, which paints about 30ms
    later because the board is larger.
