v103 - The catalogue stops contradicting itself.

  - A row read "Coming Soon | active | Live" across three columns and looked
    like three answers to one question. Two of those are the same fact in
    different words: "Stored as: active" printed the raw database value one
    cell away from a control reading "Live". That column is gone. The control
    already shows the stored status, so showing it twice added nothing but
    the confusion.
  - The columns are now "Customers see", "You set", and "Why the difference".
    The first two match on every row unless a capability gate is holding the
    service back, and then the third says which gate and what it means.
  - The reason wraps instead of truncating. It read "No prov... so the s..."
    in the width available, which tells nobody anything. It now says the
    supplier is not contracted yet and that your choice is saved and applies
    the moment one is.

v102 - The Service Catalogue is editable.

  - Every row now carries a Live / Coming soon / Disabled control, saved as
    soon as it is changed. The page was read-only because five rows -
    airtime, data, electricity, vouchers, bill payments - have a status
    DERIVED from whether a supplier can transact, so a toggle on those would
    have stored one thing and returned another. Refusing the control on the
    whole catalogue for that reason was the wrong trade: Events, Shop
    Marketplace, Virtual Doctor and Travel are held at their stored status
    and nothing else.
  - The capability gate is NOT weakened. The control writes the STORED
    status; what a customer is served still passes through the gate. Setting
    a gated service live stores "active" and still serves "coming soon",
    which is the protection that stops somebody paying for something no
    supplier can fulfil.
  - The difference is that you are told. A save that the gate overrode says
    so in the same breath: "stored as Live, but customers still see Coming
    soon until a supplier can transact." A save that took effect just says
    so plainly.
  - The gate card no longer claims there is nothing to switch on, because
    that sentence became false the moment the control existed, and an
    operator believes the sentence over the widget.
  - No API change. PUT /services/admin/:id already existed, already applied
    the gate on the way back, and already wrote an audit entry.

v87 - A failing panel now says what is actually wrong.

  - The Compliance Dashboard read "Requires API build 15" whenever a panel's
    endpoint did not answer. It was never a build check: it is the fallback for
    ANY failure, so on a server already running build 25 it sent the operator
    off to redeploy the API, which was not the problem. It now says the panel
    could not load and names the command that reports the real reason.
  - That command is new: run `npm run db:diagnose` in the API directory. It
    lists which tables each console page needs, which are missing, and prints
    the actual database error behind every panel that fails. It only reads, so
    it is safe against production.
  - Requires API build 28.

v86 - Security Content: two corrections found by review.

  - The provenance line no longer fails open. It tested a positive flag, so an
    API that does not send "stored" (anything before build 26) was read as
    "nobody has edited this yet" and printed over a colleague's live wording -
    the exact mistake the line exists to prevent. A missing field now reports
    that the API cannot tell us, which is the truth.
  - Retry load says what happened. Against an API that is still down it
    repainted byte-identical markup with no spinner and no message, which is
    indistinguishable from a dead button.
  - The customer preview draws the warning card in the app's warning pink
    instead of the console's blue. The panel promises "how the card reads in
    the TitoPay app", so an operator judging whether a warning reads urgently
    enough has to be looking at the real thing.
  - Requires API build 27.

v85 - Security Content hardening.

  - Save is now DISABLED when the stored content could not be read. The page
    already warned that saving would overwrite whatever was really stored, but
    the button beside the warning still worked, so the guard was a suggestion.
    A "Retry load" button replaces it, and submitting with the keyboard is
    refused too.
  - The icon picker offers exactly the icons the API accepts. It offered 16 of
    them while the API accepted 84, so opening content whose icon came from
    outside those 16 and pressing Save quietly rewrote it to "shield". Both
    sides now carry the same curated list of 29, and the API test suite fails
    if they drift apart.
  - The page says whether it is showing saved copy or the wording TitoPay ships
    with, and when a person last saved it and who. Those looked identical on
    screen before, so an operator could not tell whether they were revising a
    colleague's work or writing the first version.
  - Requires API build 26, which fixes a save that stored the content and then
    answered 500.

v75 - Event Tag management joins the ticketing console.

  - An approved event that has cashless Event Tags switched on gains an Event
    Tags action in the Event Approval Queue. It opens a panel over the queue
    showing tags issued, active, lost or blocked and replaced, the tap payments
    and tap sales taken from the transactions ledger rather than a separate
    tally, sales broken down by vendor and terminal, and the merchants
    authorised to take tag payments at that event.
  - Support can block a tag from the panel, with a required reason, and read
    any tag's full append-only history. Blocking stops the tag paying
    immediately and moves no money - an Event Tag holds no balance, so there is
    nothing on it to lose. The panel deliberately shows no balance column and
    offers no way to load funds, because neither exists.
  - The panel is behind a new event_tags permission, granted to Customer
    Support, Compliance and Finance in addition to the platform-owner roles.
    Marketing holds ticketing for sales reporting and does not receive it -
    disabling an attendee's wristband is a support and fraud action, not a
    reporting one. Widening it later needs no console change; the existing
    admin_role_permission_overrides setting covers it.
  - Admin can look, and can change a tag's status. Admin cannot mint, assign or
    replace a tag; those stay with the organiser and the gate.
  - Requires the API package of the same date, which adds the Event Tag
    endpoints and the permission. Without it the button does not appear,
    because the console only offers it for events the API reports as cashless.
