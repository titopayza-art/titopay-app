TitoPay Admin build: admin-console-v88-20260816

v88 (this build): the customer's Limits & Verification screen is operated
from here.

  THE NUMBERS. The whole limit framework used to be one textarea of raw JSON.
  It worked, and it was the wrong instrument: changing "Send per payment" for
  one level meant hand-editing a nested document where a stray comma loses the
  save and a typed "25,000" silently REMOVED a limit, because a non-numeric
  value reads as "no limit" downstream. API build 34 refuses that outright;
  this build means an operator never has to get near it.

  There is now a matrix: the seven limit rows the customer actually reads,
  down; the three levels, across; each level's name and explanation editable
  in place. Levels across rather than stacked because a limit is almost never
  decided on its own — "is R10 000 per payment right for Basic Verified?" is
  really "is it right next to R2 500 below and no limit above", and a stacked
  form makes that comparison a scroll.

  Leave a box EMPTY for no standing limit; the placeholder says so. A save
  sends all three levels in full, because the configuration merge resets any
  rail a save does not mention. A non-numeric amount is refused in the browser
  before it is sent, naming the box.

  THE WORDING. New section on the same page: the five sentences the customer
  reads around those numbers, editable and audit-logged. Two of them, the
  small print and the note for a level with no fixed limit, cannot be emptied;
  they can be reworded. The API refuses wording that claims a regulator sets
  or allows an amount, that calls it statutory or required by law, that uses
  "cash threshold" for a wallet limit, or that offers "unlimited", and it says
  which sentence and why. "Restore TitoPay's wording" puts all five back.

  Everything the form does not cover — products, risk bands, earned capacity,
  monitoring, the holding policy — is still editable as JSON, folded away
  under "Advanced". The level rows are stripped from that save so a stale
  textarea cannot undo a change made in the matrix above it.

  Every limit change still requires a stated reason, is audit-logged with the
  previous and new values side by side, is versioned, and can be restored.
