TitoPay Admin build: admin-console-v87-20260816

v87 (this build): a failing panel says what is actually wrong.

  - The Compliance Dashboard read "Requires API build 15" whenever one of its
    panels did not load. It was never a build check. It is the fallback shown
    for ANY failure of those endpoints, so on a server already running build 25
    it told the operator to deploy api.zip, which was not the problem. It now
    says the panel could not load and names the command that reports the real
    reason.
  - New: `npm run db:diagnose` in the API directory. It lists the tables each
    console page needs, says which are missing, and prints the actual database
    error behind any panel that fails. It only reads, so it is safe to run
    against production at any time.

Carried from v85 and v86 (Security Content):
  - Save is disabled when the stored content could not be read, with a Retry
    load button in its place.
  - The icon picker offers exactly the 29 icons the API accepts, so re-saving
    can no longer downgrade a stored icon.
  - The page says whether it is showing saved copy or the wording TitoPay ships
    with, who last saved it and when. A missing field is reported as unknown
    rather than as "nobody has edited this yet".
  - The customer preview draws the warning card in the app's warning pink.

Upload notes:
  - REQUIRES api.zip build 28. Older builds fail two admin saves outright: the
    security content save and the RBAC role save both stored their change and
    THEN answered 500, because the audit write put a name into a UUID column.
  - Asset stamp moves to admin-console-v87 across all 66 HTML files, so
    operators cannot be served a cached admin.js.
  - No new directories and no new endpoints.
  - Replace the whole admin directory as usual. Nothing under api/ or the
    website bundle is touched.

If a console page is blank or erroring after upload:
  1. cd into the API directory (the same place `npm start` runs from)
  2. npm run db:diagnose
  It will name the missing tables, or confirm the database is not the cause.
