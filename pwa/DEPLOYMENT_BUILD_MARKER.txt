This build — "where do I link my wristband?":

  LINK WRISTBAND IS NOW ON THE TICKET. It used to be a separate card
  floating above the list, which is not where anyone looks: someone
  linking a wristband is looking AT THEIR TICKET. The button now sits
  with Download PDF, Email ticket and Add to Apple Wallet, and the
  ticket's footer explains the event is cashless when it is. The separate
  card is gone — one door, not two.

  It still appears only when the server says that ticket can take a tag:
  valid ticket, approved AND cashless event, nothing linked to it yet.
  The app does not second-guess that rule; it asks.

Also in this build — a wristband button that could vanish without saying why:

  "Link Event Tag" was never removed. It appears when the server lists a
  ticket as linkable: the ticket is valid, its event is approved AND
  cashless, and no tag is on that ticket yet. When one of those is not
  true the button is correctly absent.

  What was wrong is what happened when the LOOKUP FAILED. Both tag calls
  were wrapped in a catch that returned an empty list, so a 500, an
  expired session or a weak signal produced exactly the same screen as
  "this event is not cashless" — no button, no message, no way to tell
  the two apart. Someone who knows the feature exists is left thinking it
  was taken away.

  My Tickets now says so: "Wristbands could not be checked — your tickets
  are fine and unchanged", with Try again. The tickets themselves are
  never held back by a tag failure.

  IF THE BUTTON IS STILL MISSING with no such notice, the event is not
  cashless for that ticket. On the business side: Ticketing → Event Tags →
  Cashless → pick the event → On → Save cashless setting. Then reopen My
  Tickets.

Previous build — organisers can export the tags they just issued:

  EVENT TAGS: the panel that lists freshly issued blank tags now offers
  "Download CSV" — number, tag reference, tag credential, event and the
  time issued. On a phone it goes through the share sheet where one
  exists (pick Files), and falls back to an ordinary download.

  It is built ON THE DEVICE, from the batch still on screen. It has to
  be: TitoPay keeps only a hash of every credential, so no server could
  produce this file later and none should be able to. Tapping "Done, hide
  these" drops the readable copy from memory as well as from the screen —
  after that, the export is gone and a tag would have to be reissued.
  The panel says plainly what the file is: the only readable copy that
  will exist, to be kept like cash and deleted once the tags are written.

  HARDENED WHILE THERE: every CSV the app generates - tag exports,
  transaction exports, the bulk-distribution template - now neutralises
  cells that open with = + - or @. Those are executed as formulas by
  Excel, Numbers and Sheets, and anyone can name an event. Verified with
  an event literally named =cmd|calc!A1.

Previous build — an identifier comes off the screen, and TitoKids co-parents:

  MY WORKPLACES no longer prints your own @username into its help text.
  Nothing was ever public — that panel renders only inside your own
  signed-in session, and a @username is a payment handle rather than a
  credential — but it did not need to be on screen, least of all in a
  panel people screenshot and send to someone else when asking for help.
  It is now a "Copy my @username" button: the handle goes to the
  clipboard when you choose to share it, and a screenshot carries
  nothing. api/test/pwa-identifier-exposure.test.js fails if any screen
  starts printing the account's own username, email or phone as visible
  text again (the Profile screen, which is your own detail page, stays
  the deliberate exception).

TitoKids co-parents:

  Raising a child is rarely a solo job, and neither is paying for one. A
  parent can now invite another adult — the other parent, a guardian, a
  grandparent — to help manage ONE child's wallet. It is per child, never
  per family: being trusted with one child's money says nothing about
  another's.

  THE MONEY ANSWER, said plainly on the screen: a co-parent adds money
  from THEIR OWN wallet. They can never spend the parent's. This is not a
  policy in code comments — funding debits whoever performs it, and the
  live harness proves the owner's balance does not move when a co-parent
  funds.

  What a co-parent can do: add money from their own wallet, pay for a
  need, set limits and category switches, and answer the child's requests
  (approving funds it from their own wallet). Both approvers are alerted
  when a child asks; whoever answers first settles it.

  What stays with the parent who set the wallet up: inviting and removing
  co-parents, and removing the child.

  An invitation must be ACCEPTED. Until then it grants nothing — the
  child stays invisible to the invitee. Invitations appear at the top of
  TitoKids with Accept and Decline, and arrive by in-app alert and email.
  Either side can end the arrangement, and access stops immediately.
  The child can never be made a manager of their own limits.

Proven: verification/titokids-live.js 15/15, six of them new — strangers
refused, an unaccepted invitation grants nothing, the child cannot manage
themselves, a co-parent funds from their own wallet while the owner's
