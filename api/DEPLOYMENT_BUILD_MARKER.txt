WHAT CHANGED

1. LIMITS. THREE LEVELS, and the whole ladder moved up:

       Unverified       R25 000 a month   (was R5 000)
       Basic verified   R200 000 a month  (was R25 000)
       Fully verified   no standing limit on any rail

   Enhanced due diligence is NOT a fourth level and is not described as one:
   it is a review that can open on any level, and the account keeps working
   and keeps its level while it runs.

   The per-payment, per-day, withdrawal and maximum-balance rails on the two
   limited levels moved with their monthly figure and kept their original
   proportions, so the ladder stays coherent (a day never allows more than a
   month, one payment never exceeds a day, cash out is never looser than
   paying). Basic verified is now R80 000 per payment and R160 000 per day.

   READ THIS BEFORE YOU DEPLOY. This ladder is set deliberately ABOVE the
   identity assurance the platform currently holds, and the config file says
   so in full. Unverified means NOTHING is known about the customer, and
   R25 000 a month now passes through such an account. Basic verified proves
   only that someone entered a well-formed document number no other account
   is using: no Home Affairs match, no document image, no liveness check, and
   R200 000 a month now rests on that. The exposure is carried by monitoring
   and the risk engine rather than by identity until a verification provider
   is wired in behind KYC_PROVIDER.

   Two knock-on effects to review with compliance, both console-editable and
   NEITHER changed by me, because inventing risk parameters is not mine to do:
     - monitoring.velocityAmount24h is R150 000, and basic verified may now
       send R160 000 in a day. Ordinary permitted behaviour can therefore
       raise a velocity signal.
     - edd.singleTransactionReview is R100 000, above the new R80 000
       per-payment cap, so the value trigger for EDD is now only reachable
       at fully verified.

   These are TitoPay operational limits under its RMCP, editable in the
   console without a deploy, versioned and reversible. No figure is a
   statutory threshold and the app never presents any of them as one.

   No fee, no pricing rule and no transaction rule changed. The product caps
   on the gift rail (R5 000 a gift) and the QR rail (R10 000 a scan) are
   unchanged, and they still narrow every level.

2. PROVIDERS ARE NOW REPLACEABLE. Core asks for a CAPABILITY and never for a
   company: processPayment(), processPayout(), verifyIdentity(),
   verifyBusiness(), purchaseAirtime(). Which supplier answers is one server
   side environment variable per capability:

       PAYMENT_PROVIDER=peach_checkout      (default, unchanged behaviour)
       PAYOUT_PROVIDER=peach_payouts        (default, unchanged behaviour)
       KYC_PROVIDER=internal                (default)
       AML_PROVIDER=internal                (default)
       VAS_PROVIDER=none                    (default)

   Leave all of them UNSET and the API behaves exactly as build 29 did. The
   variables exist so a supplier can be changed without a code change.

   The console's routing page no longer names an identity verification vendor
   as the default. It reads "Not configured", because none is contracted.

3. A BUSINESS IS NO LONGER A PERSON. A business now has its own entity, its
   own registration number where its type has one, and its own KYB status.
   One verified person can hold several businesses without re-verifying
   themselves once, and a sole proprietor or informal trader is never asked
   for a registration number they do not have.

MIGRATION

   node scripts/apply-migrations.js
   (or npm run db:apply-migrations, from the API directory)

   New: 20260816_business_entity_verification. It is purely ADDITIVE — three
   new tables and their indexes. It drops nothing, alters no existing column,
   rewrites no row, and touches no user, wallet, transaction, merchant or
   existing business account. The service also creates these tables on first
   use, so the API works before the migration is applied.

IF A CONSOLE PAGE OR A SAVE FAILS AFTER UPLOAD

   cd into the API directory (the same place `npm start` runs from)
   npm run db:diagnose

   It now also prints which provider supplies which capability, so
   "is the KYC provider live?" is one command instead of an investigation.

NOTHING ELSE MOVED

   No fee, no pricing rule, no wallet, no ledger, no authentication path, no
   permission and no existing endpoint changed. Withdrawals, top-ups, QR
   payments, ticketing, stokvels, TitoKids, merchant and staff flows all run
   the same code they ran in build 29 — the payment and payout calls simply
   arrive through the capability layer instead of by name.
